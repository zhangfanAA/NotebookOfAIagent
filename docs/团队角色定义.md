## 二、角色详细定义

### 角色1: ARCH - 技术总监/架构师

**核心职责:**
- 深度分析项目需求文档，拆解为可执行的技术任务
- 设计系统整体架构和技术选型
- 将任务分配给 FULL 和 RAG 两个子角色
- 维护"已开发文档"：记录已完成的功能、接口、配置
- 维护"待开发文档"：结合项目进展动态更新待办任务
- 协调两个子角色之间的接口对齐和技术沟通
- 代码审查和质量把控

**文档维护职责:**
| 文档类型 | 更新时机 | 内容 |
|---------|---------|------|
| 已开发文档 | 每个功能完成时 | 功能说明、接口定义、使用方法、测试结果 |
| 待开发文档 | 每轮迭代开始时 | 优先级排序的任务清单、依赖关系、预估工时 |
| 架构决策文档 | 重大技术选型时 | 方案对比、选型理由、风险评估 |

---

### 角色2: FULL - 全栈开发工程师

**核心职责:**
- 前端开发: Streamlit UI 界面设计与实现
- 后端开发: API 接口、路由、服务编排
- 数据处理: PDF/文档解析、数据清洗、格式转换
- 系统集成: 将各模块串联为完整可运行的系统
- 编写单元测试和集成测试

**技术栈:**
- 前端: Streamlit, HTML/CSS, 组件库
- 后端: Python, FastAPI/Flask, LangChain
- 数据处理: PyMuPDF, unstructured
- 部署: Docker, 本地服务管理

**与其他角色的协作:**
- 向 ARCH 汇报进度，接收任务分解
- 与 RAG 对接: 定义数据格式、向量库接口、Agent调用协议
- 接收 RAG 提供的模型/检索接口，集成到前端和后端

---

### 角色3: RAG - AI/RAG技术工程师

**核心职责:**
- 向量数据库搭建: Chroma/FAISS 配置与优化
- 嵌入模型集成: BGE-M3 本地部署与调优
- LangGraph Agent 开发: 状态机设计、节点实现、边路由
- LLM 集成: Ollama + Qwen2.5/Llama-3 调用封装
- 多模态支持: Qwen-VL 图片/公式识别
- 检索优化: Chunking策略、混合检索、重排序

**技术栈:**
- AI框架: LangGraph, LangChain, Ollama
- 向量库: Chroma, FAISS
- 嵌入模型: BGE-M3
- LLM: Qwen2.5-7B, Qwen-VL
- 评估: 相关性评分、答案质量评估

**与其他角色的协作:**
- 向 ARCH 汇报进度，接收任务分解
- 与 FULL 对接: 提供标准化的 Agent 调用接口
- 向 FULL 提供: 向量库查询API、Agent执行API、模型推理API

## 三、协作工作流

### 3.1 任务流转规则

`
1. ARCH 分析需求 → 拆解任务 → 写入"待开发文档"
2. ARCH 将任务分配给 FULL 或 RAG (明确边界和接口)
3. FULL/RAG 完成开发 → 更新代码 + 提交测试
4. ARCH 审查代码 → 更新"已开发文档" + 更新"待开发文档"
5. 循环迭代...
`

### 3.3 沟通协议

- **日常沟通**: 通过文档异步沟通，减少阻塞
- **技术分歧**: ARCH 做最终决策，记录决策理由
- **接口变更**: 必须提前通知对方，同步更新接口文档
- **进度同步**: 每个功能点完成后，更新已开发/待开发文档

## 四、开发节奏

| 阶段 | 目标 | 负责人 | 产出 |
|------|------|--------|------|
| Phase 1 | 数据准备与预处理 | RAG主导, FULL辅助 | 向量库就绪 |

## 五、质量标准

- 每个函数/方法必须有 docstring
- 接口变更必须同步更新文档
- 已开发功能必须有基本测试
- 代码提交前必须通过 ARCH 审查
- 文档必须反映最新状态，不允许过期
