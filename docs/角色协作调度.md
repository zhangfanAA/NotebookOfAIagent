## 二、如何启动角色

### 方法一：单角色启动（推荐用于日常迭代）

在对话开始时，用以下提示词启动对应角色：

---

**启动 ARCH：**

```
请读取 roles/ARCH.md，你现在是 ARCH（技术总监）。
当前项目文档在 docs/ 目录下。
请先阅读 docs/待开发文档.md 和 docs/已开发文档.md，
分析当前项目状态，然后告诉我下一步应该做什么。
```

**启动 FULL：**

```
请读取 roles/FULL.md，你现在是 FULL（全栈开发工程师）。
当前任务是：[粘贴 ARCH 分配的任务描述]
请按照角色要求完成开发，并在完成后向 ARCH 报告。
```

**启动 RAG：**

```
请读取 roles/RAG.md，你现在是 RAG（AI/RAG技术工程师）。
当前任务是：[粘贴 ARCH 分配的任务描述]
请按照角色要求完成开发，并在完成后向 ARCH 报告。
```

---

### 方法二：协作模式（适合一个完整迭代）

先启动 ARCH 进行任务规划，然后分别启动子角色执行：

```
Step 1:
  "请读取 roles/ARCH.md，分析当前项目状态，为本轮迭代规划任务分配。"

Step 2（ARCH 规划完成后）:
  "请读取 roles/RAG.md，执行以下任务：[ARCH 分配给 RAG 的任务]"

Step 3（RAG 完成后）:
  "请读取 roles/ARCH.md，审查 RAG 的输出，更新文档。"

Step 4:
  "请读取 roles/FULL.md，执行以下任务：[ARCH 分配给 FULL 的任务]"

Step 5（FULL 完成后）:
  "请读取 roles/ARCH.md，审查 FULL 的输出，更新文档，规划下一轮。"
```

## 三、角色间沟通协议

### 3.1 任务分配流

```
ARCH  ──任务描述──→  FULL / RAG
                     │
                     ▼
               完成开发
                     │
                     ▼
FULL/RAG  ──完成报告──→  ARCH
                     │
                     ▼
               ARCH 审查
                     │
              ┌──────┴──────┐
              ▼              ▼
         审查通过        需要修改
              │              │
              ▼              ▼
     更新已开发文档    退回修改意见
     更新待开发文档    → 子角色重新修改
```

### 3.2 接口对齐流（FULL ↔ RAG）

```
ARCH 定义接口契约
        │
        ├──→ RAG: 按契约实现接口
        │
        └──→ FULL: 按契约调用接口

接口冲突时:
  FULL/RAG 向 ARCH 提出分歧 → ARCH 做最终决策 → 更新接口契约
```

### 3.3 报告与文档更新

每个功能完成后，必须触发以下动作：

```
子角色提交完成报告
        │
        ▼
ARCH 审查代码（参考 roles/ARCH.md 中的审查清单）
        │
        ├── 更新 docs/已开发文档.md（记录新完成功能）
        │
        └── 更新 docs/待开发文档.md（标记已完成，发现新任务时追加）
```

## 七、文档维护规则（ARCH 专属）

### 已开发文档 更新规则：
```
✅ 任一功能验收通过时，立即更新
✅ 记录：任务ID、完成时间、负责人、实现文件、接口、测试结果
✅ 接口清单表同步更新状态（🔴→🟡→🟢）
✅ 重要技术决策记录理由

❌ 禁止出现已实现但未记录的功能
❌ 禁止留下过期的接口状态
```

### 待开发文档 更新规则：
```
✅ 新需求来时，ARCH 拆解为任务写入
✅ 任务完成后，移除或标记 ✅
✅ 依赖关系图随任务完成动态更新
✅ 发现技术债务时追加到"技术债务"区域

❌ 禁止留下已完成但未移除的任务
❌ 禁止没有验收标准的任务条目
```
